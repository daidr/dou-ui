# DouUI 开发者体验评审（DX 评审）

站在“拿 DouUI 写应用的人”的角度评审一个 PR：这个 API 好不好猜、和库里其他地方是否一致、照着文档能不能直接用起来、用错时有没有提示、放进 Vite / Nuxt 项目里会不会出问题。

每个 PR 有自己的 DX 评审讨论串，名字固定为 **`DX评审 #<PR 号>`**，一个讨论串只评审这一个 PR。多个 PR 可以同时各自评审，互不等待。

DX 评审串只找问题、复查、下结论，**不写修复，也不合入**。问题全部交回实现串去改。

## 和 dou-pr-review 的分工

同一个 PR 会同时有两个评审串：`dou-pr-review`（PR 评审串）和本 skill（DX 评审串）。两边按下表分工，各自只主动检查自己那一列，避免重复劳动、重复发意见。

| 方面       | DX 评审（本 skill）                                                                                                        | PR 评审（dou-pr-review）                                      |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| API        | 命名、跨组件跨包一致性、v-model / props / 事件 / 插槽 / 暴露方法的设计、默认值                                             | 不主动查（它的 E 节由本 skill 负责）                          |
| 类型       | 导出类型、泛型、字面量联合、回调参数、`checkUnknownProps` 下的报错                                                         | —                                                             |
| 集成       | 按需引入与解析器、Nuxt 模块、样式入口、包导出、服务端渲染时使用者写法会不会报错                                            | 服务端渲染时组件自身的定时器、数据加载，`docs:build` 能否结束 |
| 出错时     | 错误信息、开发环境警告是否说清楚原因和改法                                                                                 | 错误输入下界面是否崩、空状态是否好看                          |
| 文档       | 照着文档能不能把功能用起来：代码能否复制运行、API 表和类型是否一致、限制和“需要自己做的事”是否写明、示例是否展示了各种状态 | 措辞、章节编排、文案风格（它的 G 节）                         |
| 键盘与读屏 | 同一个按键、同一种播报在各组件里含义一致；`aria-*` 落在正确的元素上                                                        | 按键是否生效、焦点环、浮层关闭                                |
| 界面       | 只看“会不会让使用者用错”（如开关显示为开却没效果）                                                                         | 尺寸、对齐、测量、视觉语言、动效、性能、拖动过程中的反馈      |
| 合入       | 不合入；结论是合入的前提之一                                                                                               | 两边都通过后由它合入                                          |

顺手看到了对方范围里的问题，不要丢：照常写进报告，标上“（PR 评审范围）”，一起发给实现串，并在 PR 评审串里留一句，免得两边各发一遍。对方已经提过的问题，不再重复发。

## 讨论串的开启与收尾

- **协调者开串**：PR 开出来后（或实现串说可以评审了），协调者开一个名为 `DX评审 #<PR 号>` 的讨论串，在开串消息里写明 PR 链接、实现串的 id、这次改了什么。一个 PR 只开一个 DX 评审串；同时有几个 PR 待评审，就同时开几个串。
- **同一个 PR 后续推送**：由同一个 DX 评审串复查，不另开新串。
- **PR 被拆分或换了号**：新号重新开串，旧串在报告里写明去向后归档。
- **收尾**：结论“通过”，并且实现串确认没有遗留问题后，告诉协调者和 PR 评审串，然后归档（resolve）本讨论串。PR 被关闭不再合入时，也直接归档。

## 流程

1. **确定范围**：读 PR 描述、改动文件、实现串里的需求。列出新增或改动的公开 API：组件、prop、事件、插槽、暴露方法、组合式函数、导出类型、包入口、样式入口、Nuxt 模块选项、解析器行为。改了共享的东西，就 `grep` 一遍所有用到它的组件和包。
2. **检出并跑检查**：检出 PR 分支，`bun install`，`bun run check`。检查不通过，先把失败的输出发给实现串，再继续评审能评审的部分。
3. **先当使用者**：只看文档页，不看源码，写一个小例子把功能用起来（见“方法”）。
4. **按清单逐项检查**：A–I 节逐条过，和这个 PR 无关的项写“不涉及”。
5. **最后读源码**：确认现象的原因，再 `grep` 同类写法，看是不是一类问题。
6. **写报告**：见“报告与结论”。
7. **交回实现串**：把**所有**问题（不论高低，包括“先记一笔”的小事）一条一条发给实现串，请它每条都修，或者给出理由。只写在报告里不算交回。
8. **复查**：实现串推送后，从第 2 步重来一遍。不只看改了的那几条，改名、改类型常常会带出新的不一致。复查结果追加到同一份报告。
9. **下结论**：在报告最后和讨论串里写结论，通知实现串、PR 评审串和协调者。

## 方法

### 先用，再读

- 探针组件写在 `playground/src/dx/`，探针测试写在 `packages/<包>/src/__dx__/`，**都不提交**。需要留档的探针代码复制到报告目录。
- 凭直觉写 prop、事件、插槽名。第一次猜错的地方，就是一致性问题的线索，记下来。
- 用和其他组件一样的方式组合：放进 `DouForm`、`DouTable` 的插槽、`DouDrawer` 里，和同一行的 `DouButton`、`DouInput` 一起用，看 `size`、`disabled`、`v-model` 能不能自然地配合。

### 类型检查两遍

1. 默认配置跑 `vue-tsc --noEmit`。
2. 在探针用的 tsconfig 里打开 `vueCompilerOptions.checkUnknownProps` 和 `checkUnknownEvents` 再跑一遍。

默认配置下写错的 prop 会被当成 HTML 属性透传，不报错，第二遍才能看出“写错了却没有提示”的地方。两遍的差别要写进报告。

### 像使用者那样安装

改到包的入口、`exports`、样式入口、解析器、Nuxt 模块、`peerDependencies`、worker 或其他单独打包的文件时，不能只在仓库里用 workspace 链接试：

1. `bun run build`，把相关的包打成 tgz（`bun pm pack`）。
2. 在仓库外的临时目录里从零新建项目：一个 Vite + Vue 项目，一个 Nuxt 4 项目（改到 Nuxt 相关时）。
3. 用 tgz 安装，按文档的“快速上手”和本功能的写法接入，跑开发服务器和生产构建。
4. 看：能否解析、样式是否齐全且没有多余（记下 CSS 体积）、服务端渲染输出、浏览器控制台、构建警告。

### 跑边界数据

空数组、只有一项、全部相同、`null` / `undefined` / `NaN`、超长文字、中文、很多项、受控值在外部被改、组件挂载后再改 prop。“很多项”要真的在浏览器里看：步骤、标签页、选项放到 8 个以上，横排的东西不能撑出容器。

把组件放进它真正会用到的地方再用一遍，比如表单设计器的设置面板、抽屉、窄侧栏，不只在示例页里用。拖动、浮层这类挂到 `body` 上的东西，在这些地方最容易和原位置对不上。

### 在浏览器里用

文档站 `bun run docs:dev --port 5199`。桌面 1280 和手机 390（`isMobile: true, hasTouch: true`）各走一遍本功能的文档示例，收集控制台报错和警告。界面细节的测量交给 PR 评审，这里只看“使用者会不会因此用错或卡住”。

手机上要把桌面能做的事都做一遍：鼠标悬停才出现的信息（问题说明、提示）在手机上怎么看到；在最矮的示例（单行输入框、两三行的编辑器）里选文字、看提示；弹出键盘再收起后页面还能不能滚动。任何一项在手机上做不到，就是“使用者会卡住”。iOS 特有的行为在报告里列出来请用户在 iPhone 上确认，细节检查见 `dou-pr-review` 的“手机键盘与系统文字交互”。

## 清单

### A. 命名与跨包一致性

对照 `docs/guide/philosophy.md`，并且横向比较所有包（`dou-ui`、`@dou-ui/*`），不只比较同一个包。

- [ ] `size` 取 `sm / md / lg`；会和其他控件放在同一行的组件都支持 `size`。
- [ ] 语义色用 `tone`，不另起 `danger`、`type`、`status` 之类的布尔或枚举。
- [ ] 显隐用 `open` + `v-model:open`；展开、选中、当前项等状态都有对应的 `v-model:xxx`。
- [ ] 同一个概念全库同名：加载中 `loading`、格式化 `format`、无障碍名称 `ariaLabel`、只读 `readonly`、禁用 `disabled`、数据数组（`items` / `options` / `data` 的分工和已有组件一致）。
- [ ] 同名 prop 类型一致：`format` 不能这里是函数、那里是格式字符串；`worker` 不能这里是布尔、那里是实例。
- [ ] 同类东西的标识用同一个词：区分实例用 `id`，区分扩展里定义的种类用 `name`/`type`，不出现 `key`（和 Vue 的 `key` 混淆）。
- [ ] 位置、范围、尺寸的写法和已有 API 一致：`min` / `max`、`start` / `end`、`pos` / `line`、`width` / `height`，不另起 `range`、`from` / `to` 等同义写法。
- [ ] 默认值方向一致：同类组件的 `readonly`、`clearable`、`virtual` 等默认值相同，不一个默认开、一个默认关。
- [ ] 一个名字只有一个意思：prop 名不和参数对象里的字段同名却含义不同（如布尔开关 `search` 和要查的文字 `search`）。
- [ ] DOM 约定统一：`data-*` 标记（如“不拖动”）、CSS 变量、类名前缀各包写法相同，最好共用一个。
- [ ] 中文名、英文名和文档标题一致；组件改名后，示例、文档、类型、解析器、Nuxt 模块都跟着改。

### B. v-model、props、事件、插槽、暴露方法

- [ ] 每个 `update:xxx` 都有同名 prop；受控和非受控都能用：不写 `v-model` 时组件自己维护状态，写了以后外部修改会同步进来。
- [ ] `change` 表示“值已确认”（失焦、松手、选中、提交），不是每次输入；同名事件在各组件里的参数含义一致。含义不同的（如编辑事务）另起名字，如 `transaction`。
- [ ] 事件参数是对象时字段名和 prop 一致；同一组回调的参数形式一致（都用对象参数，都能拿到 `signal`）。
- [ ] 图标通过插槽或数据项的 `icon: Component` 传入，组件本身不加 `icon` 字符串 prop。
- [ ] 插槽名和作用域参数与同类组件一致（`default`、`empty`、`header`、`footer`、`item` 等），参数有类型。
- [ ] 暴露方法的名字是动词（`focus`、`open`、`scrollTo`、`exportPNG`），返回值有类型；需要异步的返回 Promise。组件内部能拿到的信息（如分组好的列表），放在组件外的面板也能通过暴露方法或导出函数拿到。
- [ ] 未声明的属性有确定的落点（philosophy 第 11 条）：`class`、`style` 落在根元素，`aria-label`、`name`、`autocomplete` 落在真正的可交互元素上。
- [ ] 不内置业务策略（存储、请求、权限、上传地址），状态通过 `v-model` 和事件交给应用；需要应用提供的东西通过 prop 或回调传入。

### C. 类型

- [ ] 公开的 prop、事件、插槽、暴露方法、扩展接口的类型都从包入口导出，名字和组件对应（`XxxProps`、`XxxEmits`、`XxxExpose`）；导出了的类型确实被组件使用。
- [ ] 可选值是字面量联合，不是 `string`；数据项、回调参数有具体类型，不是 `any`。
- [ ] 泛型能从数据推断（`items` 的类型带到插槽参数、事件参数里），不需要使用者手写断言。
- [ ] 用 `checkUnknownProps` 跑一遍探针：写错的 prop、事件能报错；文档示例在这个配置下也没有报错。
- [ ] 文案覆盖、配置对象这类嵌套参数用 DeepPartial，局部覆盖一项时其他项不丢（深合并）。

### D. 扩展接口与回调

适用于有扩展系统、自定义渲染、自定义校验、协同编辑接口的组件（编辑器、流程、甘特、表格、图表、表单设计器、数据透视、仪表盘、代码编辑器）。

- [ ] 扩展的定义方式和其他包一致（`defineXxx` 帮助函数、`name`、`priority`、上下文 `ctx` 的形状）；有差别的地方文档写明原因。
- [ ] 回调在什么时候调用、调用多频繁写清楚（如拖动中对每个候选端口都调用，提醒不要做耗时操作）。
- [ ] 异步回调能取消（`signal`），组件卸载、条件变化时会取消。
- [ ] 资源由谁创建由谁释放写清楚：worker、订阅、协同连接、对象 URL。
- [ ] 协同编辑：本地和远端用同一个数据结构；颜色、用户名、光标等参数名和其他包一致（如 `collaborationColors`）。

### E. 集成：按需引入、Nuxt、样式、服务端渲染

- [ ] 新组件、新包加进了解析器和 Nuxt 模块，自动解析能找到组件、样式入口和图标。
- [ ] 样式入口：`<包>/style` 带上依赖的 dou-ui 组件样式，`style.css` 只含本包；只用一部分（如表单渲染器、单个按钮）时，不会带上无关组件的样式。按“像使用者那样安装”实测 CSS 体积。
- [ ] 有独立子入口的部分（如 `renderer`、`scheduler`、`worker`），JS 和样式都只带上自己需要的部分。
- [ ] 文档里的写法在服务端渲染时不报错：不在 `<script setup>` 顶层直接用 `window`、`document`、`Worker`、`ResizeObserver`；需要的地方用函数或挂载后再执行，并在文档里写明。
- [ ] 在 Nuxt 4 里按文档接入，服务端输出有内容，浏览器里没有注水不一致的警告。
- [ ] 自动导入的函数（如 `toast`）在文档里的用法实际能跑通：Vite 下只能在脚本里用的，示例写在脚本里并说明。
- [ ] 没安装的可选包、缺少的 peer 依赖：报错或警告能让使用者看懂要装什么。
- [ ] 解析器、Nuxt 模块依赖的路径按项目配置（如 Vite 的 `root`）找，不依赖当前目录。

### F. 错误信息与开发环境警告

- [ ] 用错时有提示：缺少必需的注册（如字段类型没传进 `fields`）、互相冲突的 prop、不支持的组合（如雷达图和其他系列放在一起）、回退到降级路径（如 worker 里缺少语言）。不出现“悄悄失效”。
- [ ] 提示以 `[dou-ui]` 开头，写清楚是哪个组件、哪个参数、为什么错、怎么改，一条提示只讲一个原因。
- [ ] 警告只在开发环境出现，生产构建里被去掉；同一个问题不在每次渲染时刷屏。
- [ ] 抛出的错误（如 PNG 导出超出画布上限）各包行为一致，错误信息说明限制和可选的处理办法；不静默导出质量更差的结果。

### G. 文档：照着能不能用起来

措辞、章节编排由 PR 评审负责；这里只看使用者照着文档能不能做成事。

- [ ] 文档里的代码复制到新项目里能直接运行：导入路径正确（`dou-ui`、`@dou-ui/*`），用到的变量都定义了，服务端渲染安全。
- [ ] API 表和类型声明逐项一致：名称、类型、默认值；新增的 prop、事件、插槽、暴露方法、导出类型都在表里，删掉的也从表里删了。
- [ ] 使用者需要自己做的事和限制写清楚：只读一次的 prop、需要自己保存的状态、需要自己结束的资源、浏览器限制、性能上限。最好再配一条开发环境警告。
- [ ] 示例覆盖了文档讲到的每种状态：加载、出错、空、禁用、只读。一打开就能看到，不需要先点一串按钮。
- [ ] 示例里的开关、按钮都真的有效果；在某些条件下不生效的（如窄屏不显示小地图），示例里禁用并说明。
- [ ] 示例用编造的场景，人名用“戴兜”，地名用上海；配色是我们自己挑的值，不照搬别的产品。
- [ ] 跨页面的说法一致：指南、组合式函数页、生态系统页、路线图（`ROADMAP.md`）里提到这个功能的地方都同步了，不出现“文档说基于它实现，代码其实没有”。

### H. 键盘、读屏的一致性

- [ ] 同一个按键在各组件里含义一致：右方向键看下一个、Shift + 单击选范围、⌘ / Ctrl + 单击加选、Esc 取消或关闭、Enter 确认。和已有组件不同的，文档写明原因。
- [ ] 中文输入法组词时（`isComposing` 或 `keyCode === 229`），在输入框里响应 Enter、方向键的地方都不触发；用共享的 IME 工具函数。
- [ ] 读屏能读出结果：增删、移动、整理、保存、连线这类操作有播报，措辞和其他组件一致；只靠颜色或图形传达的信息有文字替代。
- [ ] ARIA 属性用在支持它的角色上（如 `aria-expanded` 配 `role="combobox"`），状态（`aria-busy`、`aria-current`、`aria-selected`）随状态更新。

### I. 仓库约定

- [ ] 改名、改类型时直接改，不留旧名字和兼容别名（项目还没发布）。
- [ ] 组件通用，不带业务内置项；业务场景放在区块或示例里。
- [ ] 代码、注释、文档、类型名里不提任何其他 UI 库或图标库，也不照搬它们的 API 名称和文档原句。
- [ ] 所有图标来自 `@dou-ui/icons`；缺图标交给图标讨论串。

## 严重程度

- **高**：照着文档用会报错、构建失败、服务端渲染崩溃、数据丢失、类型错误挡住正确写法、公开 API 明显用错名字以后很难改。
- **中**：和已有约定不一致、容易用错、用错时没有提示、文档和类型对不上、样式或体积明显多带了东西。
- **低**：细节和体验、文档里少一句说明、示例不够直观。

三级都要修好，或者由实现串给出用户也会认可的理由，才能通过。

## 报告与结论

### 存放位置

并行评审时多个讨论串会同时写共享目录，按下面的约定避免互相覆盖：

- 报告：`/mnt/project-files/reviews/dx-review/<日期>-<PR 号>-<主题>/README.md`，例如 `2026-11-01-226-sheet-functions/`。只写自己的目录。
- 截图：`/mnt/project-files/screenshots/dx-review/<PR 号>-<主题>/`。

- 不改别的讨论串的报告。

### 报告结构

```markdown
# <功能>（PR #<号>）DX 评审

- 代码：<分支> <提交>
- 范围：<新增或改动的公开 API、影响到的包>
- 方法：<探针、vue-tsc 两遍、是否用 tgz 在新项目里装过、Vite / Nuxt、桌面 / 手机>
- 检查：bun run check <通过 / 失败>
- 截图：<文本链接>

## 意见

1. **高：<一句话>** 现象、怎么复现（探针代码或截图）、和哪个已有 API 不一致、建议的改法。
2. **中：…**
3. **低：…**

## 通过的部分

按 A–I 列出确认过的项和怎么验证的；不涉及的节写“不涉及”。

## 复查（<提交>）

逐条写已修复 / 理由成立 / 还没修，以及复查时新发现的问题。

## 结论

<见下面的格式>
```

### 交回实现串

用一条消息把所有意见发给实现串，每条带编号和级别，写清楚现象和建议，附报告链接。请实现串逐条回复“已修”或“不修，理由是……”。复查时只追问还没解决的条目和新发现的问题。

PR 里顺带暴露出的、不属于这次改动的问题（例如别的包里早就存在的不一致），也写进报告，单列为“不是这个 PR 的改动”，发给协调者，由协调者转给负责那个包的讨论串，不要求这个 PR 修。

### 结论

结论只有两种，写在报告最后，也作为讨论串里的最后一条消息，并发给 PR 评审串和协调者：

```markdown
**DX 评审结论：通过** ✅

- 提交：<sha>
- 所有意见已处理（共 N 条：修复 X 条，理由成立 Y 条，见“复查”）
- 报告：<链接>
```

```markdown
**DX 评审结论：不通过** ❌

- 提交：<sha>
- 剩下的意见：
  1. [高] …
  2. [中] …
- 已交回实现串，修好后复查。
```

写“通过”的前提：

- A–I 每一节都检查过（或写明不涉及），没有剩下的意见；
- 复查用的是 PR 当前最新的提交，之后又有推送就要重新复查；
- 改动涉及包入口、样式入口、解析器、Nuxt 时，按“像使用者那样安装”实测过。

DX 评审串**不合入 PR**。PR 评审串只有在本 PR 的 DX 评审结论是“通过”、并且对应的是同一个提交时，才能合入。需要用户亲自决定的事（改变用户已经定下的 API 方向、删除功能、npm 发布），即使评审没有问题，结论也写“通过，待用户确认”。

## 发现漏检时扩充本 skill

DX 评审通过后，如果用户（或任何人、任何讨论串）又发现了本该在这次评审里查出来的使用问题，要马上复盘并扩充这份清单：

1. **复盘**：在当时的报告里追加“漏检复盘”一节：问题是什么、评审时做了什么、为什么没发现。要找到具体原因，例如“只在 workspace 里试，没有用 tgz 装”“只跑了默认的 vue-tsc”“只和同一个包比，没有和其他包比”“只看了浏览器，没在 Nuxt 里跑”，不要写“看漏了”。
2. **加检查项**：在 A–I 对应的节里加一条能直接执行的检查，写成“做什么、看什么、什么算不通过”。能用脚本或测试发现的，优先写成脚本或测试，并在清单里写明怎么跑。
3. **加一行漏检记录**：在下面的表里加一行。
4. **回头查一遍**：用新的检查项把最近合入的同类 PR 再查一遍，发现同样的问题就发给对应的讨论串修。
5. **开 PR 修改本 skill**：标题如 `docs: DX 评审清单补充<检查项>`。只新增或收紧检查项的 PR，按 `dou-pr-review` 评审通过后可以直接合入；放宽或删除检查项、改变“通过”标准、改变和 `dou-pr-review` 的分工，要等用户确认。
