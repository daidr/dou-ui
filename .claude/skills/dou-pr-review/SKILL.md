# DouUI PR 深度评审

每个功能实现或缺陷修复做完以后，都会开一个单独的 review 讨论串，用这份清单评审它的 PR。review 串只负责找问题、复查、下结论，**不替实现串写修复**；问题交回实现串去改。

结论是“通过”时，review 串可以不等用户确认，直接 squash 合入，然后归档。所以“通过”的标准是：**用户自己来验收也挑不出问题**。拿不准的地方一律算问题，不要放过。

## 流程

1. **确定范围**：读 PR 描述、改动文件列表和实现串里的需求。列出这次改动影响到的组件、页面、区块和文档示例，包括间接受影响的（改了共享组件，就要看所有用到它的地方，`grep` 一遍调用处）。
2. **检出并跑检查**：检出 PR 分支，`bun install`，跑 `bun run check`（格式、lint、类型、测试）。CI 不绿、有冲突，直接不通过。
3. **在浏览器里逐项评审**：按下面 A–F 六节逐条过。文档站 `bun run docs:dev --port 5199`，playground `bun run dev`。探针代码写在 `playground/src/dx/` 或 `packages/*/src/__dx__/`，**不提交**。
4. **写评审报告**：放在 `/mnt/project-files/reviews/pr-review/<日期>-<PR 号>-<主题>/README.md`，截图放同一目录。格式见“报告与结论”。
5. **交回实现串**：把**所有**问题（不论高低）发给实现串，每条都要修或给出理由。低优先级的也要发，不要只写在报告里。
6. **复查**：实现串推送修复后，从第 2 步重新来一遍。不只看修的那几条，改动可能带出新问题。复查结果追加到同一份报告里。
7. **下结论并处理**：
   - **通过**：确认 CI 全绿、没有冲突、分支是最新的，用 squash 合入（标题用中文、只写功能或修复，不提批次）。合入后通知实现串和协调者，归档 review 串。
   - **不通过**：列出剩下的问题，等实现串修好再复查。

## 截图与测量的基本要求

肉眼看整页截图看不出 1–2px 的偏差。之前漏掉的工具栏图标大小不一、色块不居中，都是因为只看了缩小的整页截图。

- **测量，不要目测**。尺寸、居中、间距一律用 `getBoundingClientRect()` 量出数字：
  - 改到按钮、工具栏、菜单、表单控件时，跑 `docs/scripts/audit-icons.ts`（需要先开文档站；由修复电子表格工具栏图标的 PR 加入，还没合入时用下面的 `measure.js`），它会列出图标偏离控件中心超过 0.75px、同一组里图标尺寸不一的地方。
  - 其他元素（色块、标记点、徽标、分段控件等）用本目录的 `measure.js` 在页面里量：

    ```js
    await page.addScriptTag({ path: '.claude/skills/dou-pr-review/measure.js' })
    const report = await page.evaluate(
      (selector) => window.douMeasure(selector),
      '.dou-sheet-toolbar',
    )
    ```

    它给出每个控件里图标 / 色块的尺寸、四边留白和中心偏移，并列出超过 0.75px 的偏移、同组里不一致的高度和图标尺寸。

  - 两个脚本只看得到页面当前显示的元素。**下拉菜单、弹框、选择器面板、右键菜单要先打开再量**，每个都要打开量一遍。
- **截局部、放大看**：用 `locator.screenshot()` 截控件本身，`deviceScaleFactor: 2` 或 `3`，必要时再放大到 400%。整页截图只用来看布局。
- **四种环境都要截**：桌面 1280×800 浅色、桌面深色、手机 390×844（`isMobile: true, hasTouch: true`）浅色、手机深色。深色用 `colorScheme: 'dark'`，并确认页面真的切到了深色。
- **截中间状态**：拖动、缩放、旋转、动画进行中都要截图，不只截松手之后。见 B 节。
- 截图里的中文由容器里的回退字体（Noto / 文泉驿）绘制，跟苹果系统的字体不一样；对齐结论以测量数字为准，并在报告里注明字体。

## A. UI 细节

### 尺寸与对齐

- [ ] 同一行、同一组（工具栏、按钮组、表单行、菜单）里的控件高度一致，取 28 / 32 / 40。
- [ ] 同一组里的图标尺寸一致。带下拉箭头、带文字、带徽标的按钮，图标和纯图标按钮一样大。
- [ ] 图标、色块、标记点在容器里居中：中心偏移不超过 0.5px（工具阈值 0.75px）；只有一个元素的框（色块框、图标按钮）四边留白相等。
- [ ] 菜单项的勾号、单选点、尾部图标、快捷键与文字垂直居中，同一个菜单里大小一致。单选、多选菜单用 `DouDropdownRadioGroup` / `checked`，不要自己画勾号。
- [ ] 小的圆形、居中元素（单选点、加载圈、色块）用偶数像素，不用百分比，否则落在半像素上。
- [ ] 间距用 `--dou-space-*`，相邻元素的间距在同一组里一致，左右对称。
- [ ] 文字和图标的基线、中线对齐；输入框、选择器和按钮放在同一行时，上下边对齐。

### 中文与文字

- [ ] 控件里的单行文字用 `text-box: trim-both cap alphabetic` 居中；中文不偏上也不偏下（量文字盒和控件的中心）。
- [ ] 省略号用 `overflow-x: clip` + `text-overflow: ellipsis`，不要在用了 text-box trim 的元素上写 `overflow: hidden / clip`（Safari 会把字的上下切掉）。`position: sticky` 的标签再加 `padding-block: 4px; margin-block: -4px`。
- [ ] 超长中文、超长英文单词、数字、空字符串都试一遍：不撑破布局、不重叠、截断处正确。
- [ ] 中文标点、中英混排的间距正常；示例里的人名、地名符合项目约定（人名用“戴兜”，地名用上海，不用香港）。

### 主题与屏幕

- [ ] 浅色、深色都看过：深色下没有写死的白底、黑字、浅色阴影；边线在深色下仍然可见。
- [ ] 手机 390 宽：没有横向滚动，没有被裁掉的浮层，点击区至少 40px（`pointer: coarse` 下）。
- [ ] 触屏上可以输入文字的地方字号至少 16px（用 `--dou-font-size-input-min`），否则 iOS 聚焦时会放大页面。
- [ ] 加载、空、错误、禁用、只读、选中、悬停、按下、聚焦每种状态都看一眼。

## B. 交互逻辑

### 指针、触屏、键盘

- [ ] 鼠标：悬停、按下、拖动、双击、右键各自的行为正确，光标形状和操作对应。
- [ ] 触屏：手机模拟器里用 CDP 触摸事件（不是鼠标事件）实际拖一遍。拖动不会被页面滚动打断（用共享的 `holdPointer`）；需要滚动的地方仍然能滚动；长按、轻点行为正确。
- [ ] 键盘：Tab 顺序合理，焦点环只在键盘操作时出现；方向键、Enter、空格、Esc 都有预期的效果；能完成和鼠标一样的操作。
- [ ] 中文输入法组词时（`isComposing` 或 `keyCode === 229`），Enter、方向键不触发选择或提交。
- [ ] 快速连续点击、按住不放、拖到窗口外再松开、拖动中切换标签页，状态都能恢复。

### 浮层关闭

改到或新增下拉、菜单、弹框、提示、选择器面板时，每一个都要试：

- [ ] 点外部关闭；按 Esc 关闭（焦点还在编辑器或输入框里时也要能关）；再点触发器关闭。
- [ ] 打开另一个浮层时，前一个关闭，不会两个同时开着。
- [ ] 快速点击和慢速点击结果一样；触屏上也能关闭。
- [ ] 放在 `overflow: hidden` 的容器里不会被裁掉；靠近屏幕边缘时会翻转、贴边。
- [ ] 修在共享组件里，而不是在调用处打补丁；`grep` 同类写法（`trigger="manual"`、自己维护的 open 状态、直接用 `useFloating`）一起修。

### 拖动、缩放、旋转时的实时反馈

白板缩放图片时选框停在原来的大小，就是因为只截了松手之后。

- [ ] 拖动**过程中**截图：选框、手柄、连接点、连线、浮动工具栏、对齐线都跟着当前的预览位置走，不是停在旧位置、松手才跳过去。
- [ ] 缩放、旋转、移动用同一份预览数据（如 flow 的 `ctx.previewNode`，PR #223），各部分不各自维护一份。
- [ ] 拖动中按 Esc 能取消，恢复到开始前的状态；撤销一步回到操作前。
- [ ] 手柄跟着指针走：锁定比例、对齐吸附时，手柄也不能离开指针太远。

### 画布、白板、编辑器类组件

每类元素（形状、便签、文字、图片、手绘、分组等）都要试：

- [ ] 旋转后再缩放，缩小到最小值，放大到很大。
- [ ] 选框和手柄跟着旋转，圆角保留；内容不超出选框。
- [ ] 多选后整体移动、缩放、旋转。
- [ ] 画布缩放到 50% 和 200%，手柄大小和指针位置一致。
- [ ] 手机上的手柄点击区和拖动。
- [ ] 能在 WebKit 里看就看一遍；这台机器没有 WebKit 时，在报告里写明，并请实现串说明是否在 WebKit 上验证过。

## C. 性能

- [ ] 大数据量：按组件的定位试 1 千、1 万（表格、图表、表格编辑器等试到 10 万或更多），首次渲染、滚动、交互不卡顿。下拉类超过 100 项要自动虚拟化。
- [ ] 交互时不重渲染整个列表：悬停、选中一项只更新相关的项（可以用 Vue DevTools 或在渲染函数里计数）。
- [ ] 没有 O(n²) 的查找；循环里查数组的改成 `Map` / `Set`。
- [ ] 拖动、滚动、缩放时没有强制同步布局（在循环里读 `offsetWidth`、`getBoundingClientRect` 再写样式）；高频事件用 rAF 合并。
- [ ] 全局监听只在需要时添加（浮层打开时、拖动时），卸载后都移除；定时器、Worker、ResizeObserver 都清理掉。
- [ ] 服务端渲染：服务端不加载数据、不启动定时器，`docs:build` 能正常结束。
- [ ] 能用 `bun run bench` 的就跑一遍，和 main 对比没有明显变慢。
- [ ] 打包：只引入用到的部分，没有把大依赖带进主包；新代码不使用 ES2023 的数组方法（`toSorted`、`findLast` 等）。

## D. 视觉语言

对照 `docs/guide/visual-language.md`：

- [ ] 以中性色为主，颜色只表达含义；默认 `tone` 是 `neutral`，没有默认用主色蓝的地方。
- [ ] 语气色低饱和、偏灰，不显得廉价。
- [ ] 层级先用文字灰阶、表面色、1px 细线区分，最后才用阴影。
- [ ] 控件样式：solid 有深一档的描边、顶部内高光和带色调的柔和投影；soft、outline 有细描边和静止阴影；ghost 没有边框和阴影。按下时投影消失、下移 0.5px。
- [ ] 只用 Token，不写死颜色、字号、圆角、阴影；字号只有 13 / 14 / 16，字重不超过 600。
- [ ] 圆角：控件 6、容器 12、浮层 10；靠近外层圆角时两层同心（内 = 外 − 距离），差值小于 4px 时内层保留自己的圆角。
- [ ] 焦点环 2px、间隔 2px，只在键盘操作时出现。
- [ ] 动效不超过 320ms，进场减速、退场加速，没有回弹（只有直接拖拽时允许弹性）；遵循“减少动态效果”。
- [ ] 所有图标来自 `@dou-ui/icons`；缺图标交给图标讨论串画，不在实现里自己画。纯图标按钮有 `DouTooltip`。

## E. API 与使用体验

按 `/mnt/project-files/reviews/dx-review/README.md` 的清单检查，要点：

- [ ] 命名和已有组件一致：`size`（sm / md / lg）、`tone`、`open` + `v-model:open`、`loading`、`format`、`ariaLabel`。
- [ ] 先只看文档写一个例子，凭直觉猜 prop 名；再用 `vueCompilerOptions.checkUnknownProps` 跑一遍 `vue-tsc`，找出写错但没报错的地方。
- [ ] 不内置业务逻辑，状态通过 `v-model` 和事件交给使用者。
- [ ] 文档的 API 表和类型声明一致；示例能直接运行；中文文档用平实的语气。
- [ ] 文案可以局部覆盖，嵌套对象深合并。

## F. 代码、测试与仓库约定

- [ ] 修复写在根源上（共享组件、共享工具），不是在某个调用处打补丁；同类问题一起修掉。
- [ ] 有测试覆盖这次的行为，修复类 PR 有能复现原问题的测试。不能跳过、禁用测试来让 CI 通过。
- [ ] 提交和 PR 用中文，只写功能或修复，不提批次；没有 AI 签名、会话链接；作者是 `daidr <daidr@daidr.me>`。
- [ ] 仓库里（代码、注释、文档、提交、PR）不提任何其他 UI 库或图标库。
- [ ] 改了公开 API 时，不留旧名字和兼容别名（项目还没发布）；路线图、文档同步更新。

## 报告与结论

报告 `README.md` 的结构：

```markdown
# PR #<号> <标题> 评审

- 代码：<分支> <提交>
- 范围：<改动影响的组件、页面>
- 环境：桌面 Chromium 1280 浅 / 深，手机 390 浅 / 深（触摸），<是否有 WebKit>，字体 <Noto / 文泉驿>
- 检查：bun run check <通过 / 失败>，CI <通过 / 失败>

## 问题

### 高：<一句话>

现象、复现步骤、测量数字或截图链接、建议的改法。

### 中：…

### 低：…

## 通过的检查

按 A–F 列出确认过的项，写清楚怎么验证的（量了什么、截了哪几张）。

## 复查（<提交>）

逐条写已修好 / 还有的问题。

## 结论

<见下面的格式>
```

问题分三级：**高**（错误行为、数据丢失、崩溃、无法操作）、**中**（违反视觉语言或约定、容易用错、明显的视觉偏差）、**低**（细节和体验）。三级的问题都要修好或由实现串给出用户也会认可的理由，才能通过。

结论只有两种，放在报告最后，也作为 review 串的最后一条消息：

```markdown
**结论：通过** ✅

- 提交：<sha>，CI 全绿，无冲突
- 所有问题已修复（共 N 条，见“复查”）；没有修的 M 条及理由：…
- 截图：<文本链接>
- 可以直接合入。
```

```markdown
**结论：不通过** ❌

- 提交：<sha>
- 剩下的问题：
  1. [高] …
  2. [中] …
- 已交回实现串，修好后复查。
```

**只有下面全部满足才能写“通过”**：

- A–F 每一节都过了，没有剩下的问题；
- `bun run check` 和 CI 全绿，分支没有冲突；
- 四种环境的截图都看过，测量数字都在容差内；
- 改动不涉及需要用户亲自决定的事。下面这些即使评审没问题，也写“通过，待用户确认”，不自己合入：发布到 npm、改变用户已经定下的设计或 API 方向、删除功能、修改本 skill 里放宽或删掉检查项的部分、用户明确说过要自己确认的 PR。

## 发现漏检时扩充本 skill

评审通过、合入之后，如果用户（或任何人）又发现了这次本该查出来的问题，要马上复盘并扩充这份清单：

1. **先复盘**：在对应的报告里追加“漏检复盘”一节，写清楚：问题是什么、评审时做了什么、为什么没看出来（没测到这个场景？只看了截图没量？没打开那个面板？没在那个环境里看？），找到的是原因，不是“看漏了”。
2. **加检查项**：在 A–F 对应的小节里加一条能具体执行的检查，写成“做什么、看什么、阈值是多少”，不要写“注意细节”这种无法执行的话。能用脚本测的，优先改进 `measure.js` 或 `docs/scripts/audit-icons.ts`，让下次自动发现。
3. **加一行漏检记录**：在“已知漏检记录”表里加一行（日期、问题、为什么漏掉、对应的检查）。
4. **回头查一遍**：用新加的检查项把最近合入的同类改动再查一遍，看有没有同样的问题，有就交给对应的讨论串修。
5. **开 PR 修改本 skill**：标题如 `docs: 评审清单补充<检查项>`。只新增或收紧检查项的 PR，按本 skill 评审通过后可以直接合入；放宽或删除检查项、改动“通过”标准的 PR，要等用户确认。
